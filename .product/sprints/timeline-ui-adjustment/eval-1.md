## 受け入れ条件（ユーザー指定の3点）の確認結果

### 1. タイムライン閲覧中もお題を常時表示 — 達成

- 今日のお題画面の `today.promptText`（「今日、思わず笑ってしまったことは何ですか？」）と、
  タイムライン上部 `timeline.promptText` の文字列が完全一致することを確認（E01）。
- **カード表示中・スワイプ5回後・読み切り（`timeline.exhausted`）・0件の空状態
  （`timeline.empty`）のすべてでお題が出続ける**ことを確認（E01 / E04）。
- レイアウトの重なりを実測（iPhone 17、単位pt）:
  - window `(0,0,402,874)`
  - `timeline.close` `y 85〜103` → `timeline.prompt` `y 122〜163` → カード `y 約301〜537`
    → `timeline.like` `y 676〜758` → 「いいね」ラベル `y 768〜784` → スワイプ案内 `y 798〜812`
  - 重なり0、画面外へのはみ出し0、スクロールは発生しない。
- iPhone 16e（390×844）でも重なり0。お題が2行に折り返し、strip の高さが 41 → 57.7pt に
  伸びるが、カード・いいねボタンとも画面内に収まる（E13）。
- 端末言語を英語にした疑似翻訳モードでは strip が「[EN] 今日、思わず…」の2行になるが、
  レイアウトは崩れない（E05、スクリーンショット確認済み）。

### 2. ✕（次へ）ボタンの削除・スワイプへの一本化 — 達成

- `app.buttons["timeline.next"]` は存在しない。タイムライン上のボタンを全列挙した結果は
  `["timeline.close|閉じる", "timeline.more|この回答を通報またはブロック", "timeline.like|いいね"]`
  の3つのみ（裏で生きている today 画面の2つを除く）。「次の人へ」ラベルのボタンも0件（E02）。
- **スワイプだけで12件を最後まで送り、読み切り表示に到達**（E02）。20件でも同様（E07）。
  途中で同じ回答が連続することも、詰まることも無かった。
- 読み切り画面で左右にスワイプしても壊れず、「閉じる」で今日のお題画面へ戻れる（E02）。
- 通報・ブロック直後、いいね連打制限のアラートを閉じた直後も、スワイプで次へ進める（E06 / E08）。

### 3. いいねボタンの位置・見た目 — 達成

## 安定性

- クラッシュ0。`~/Library/Logs/DiagnosticReports` に今回の検証時間帯の `SameQ*.ips` は無し。
- `log stream`（`messageType >= 16`）で拾えたアプリプロセスのエラーは、すべてシミュレータ環境由来:
  - `libFontParser ... AppleColorEmoji.ttc: No such file or directory`（このランタイムに絵文字

  起動ごとに1回出るが、**タイムラインへ直接起動した場合には一度も出ない**ことを
  `simctl launch -SameQResetViewed` ＋ `log stream` で確認した。オンボーディング／キーボード経路で

## 回帰

1. **既存フルスイート**: `SameQTests` ＋ `SameQUITests`（evaluator 追加分を除く）を
   他プロセス非併走で単独実行し **90/90 全件成功**（`** TEST SUCCEEDED **`）。
   generator の自己申告どおりであることを確認した。
2. **evaluator 独自の抜き取り**（`timeline.next` 撤去の影響を受けやすい領域を優先）:
   - スプリント04 通報・ブロック: ⋯ → 通報（理由未選択では送信不可 → 送信 → 完了 → 即時非表示）、
     ⋯ → ブロック（確認 → 完了 → 以後出ない）、どちらも直後に次の回答へ進む。お題も消えない（E06）。
   - スプリント03 既読管理: 20件を重複なしで読み切り、再起動後も既読が残り `timeline.exhausted`（E07）。
   - スプリント05 連打制限: いいね連打で日英併記の制限メッセージ →
     OK で閉じてもタイムラインは閉じず、スワイプで先へ進める（E08）。
   - スプリント06 翻訳: 翻訳ボタン・原文表示・「翻訳済み」等のUIが1つも無い（6画面分を全ラベル走査、E09）。
   - スプリント01 ロック: 未回答ではタイムライン導線が無く、スワイプでも入れない（E10）。
   - スプリント01 いいねの永続: 再起動後も押下状態（E03）。

## 改善提案（合否には影響しない）

### [A] 優先度：高 — スワイプが効くのはカードの上だけ。画面の約1/3は無反応
- **実測（E12、iPhone 17）**: 画面を水平にドラッグしたとき次へ進むかを3か所で計測した。
  - `y = 0.25`（お題の下〜カードの上の余白、約138pt幅の帯）→ **進まない**
  - `y = 0.50`（カードの上）→ 進む
  - `y = 0.68`（カードの下〜いいねボタンの上の余白、約139pt幅の帯）→ **進まない**
- **原因（推測。症状とは分けて記す）**: `DragGesture` が `cardStack` の `ZStack` ではなく
  `AnswerCardView` 本体に付いているため、カード外の余白はジェスチャを受け取らない。
- **なぜ今回問題になるか**: 以前は✕ボタンという代替手段があったので、余白でのスワイプが
  空振りしても詰まらなかった。今は前進手段がスワイプ1つだけなので、
  余白を払った利用者には「反応しない」としか見えない。
- **提案**: `cardStack` の `ZStack` に `.contentShape(Rectangle())` を付けて
  `DragGesture` をそちらへ移す（カード自体の `offset` / `rotationEffect` はそのままでよい）。
  なお `AnswerCardView` は `minHeight: 240` を持つので、カード上のスワイプは常に成立しており、
  主要動線が完走できないわけではない（だから不合格にはしていない）。

### [B] 優先度：中 — お題とカードの間の空白が大きく、カードが下に沈んで見える
- iPhone 17 でお題の下端 163pt、カードの上端 約301pt。約138ptの空白が空く。
  スクリーンショットで見ると画面上半分が空白で、視線がカードに落ち着きにくい。
- お題を常設したぶん、カードの `Spacer` 配分（`cardStack` の `.frame(maxHeight: .infinity)`）を
  見直すと収まりが良くなる。

### [C] 優先度：中 — 書き換えたUIテスト2箇所で「実際に次へ進んだ」検証が抜けた
- `SprintFiveAcceptanceTests`（旧 171行目付近／旧 201行目付近）は、以前は
  `XCTAssertTrue(app.buttons["timeline.next"].isEnabled)` で「制限後も操作できる」ことを見ていた。
  書き換え後は `app.swipeLeft()` のあと `timeline.card.body` の **存在** しか見ていないため、
  スワイプが空振りしても通ってしまう。`waitForBodyToChange` 相当で本文が変わったことまで
  見ると、元の意図に戻る（evaluator 側の E08 では本文の変化まで確認して合格を確認済み）。

### [D] 優先度：低 — 長いお題での2行省略
- `promptStrip` は `lineLimit(2)`。同梱シードの2件は iPhone 16e でも2行に収まるが、
  スプリント09（お題の自動生成）で長文お題が入ると末尾が省略される。
  generator も self-review で同じ懸念を挙げている。

## 評価できなかったもの

- **お題の「準備中…」表示の実物**。`timeline.promptLoading` を捕まえるため、端末言語を英語にして
  (a) 疑似翻訳モード、(b) 実翻訳経路の2通りで、起動直後に 40〜60ms 間隔の連写を各4〜5回、
  計 50枚以上のスクリーンショットを撮ったが、**1枚も「準備中…」を捉えられなかった**
  （シミュレータでは疑似翻訳が50msで返り、実翻訳は全ペア非対応で即座に原文へフォールバックするため、
  表示時間が概ね100ms未満）。
  代わりに次を確認した: お題が「準備中…」のまま固まることは一度も無く（毎回確定表示に変わる）、
  確定後に「準備中…」が残ることも無い。実機では ja→en が実際に翻訳されるため数秒表示される
  可能性があり、そのときの見た目は**スプリント06の実機確認（保留中）と合わせて見るのが良い**。
- Dynamic Type 拡大時の崩れ。`promptStrip` を含めアプリ全体が `.font(.system(size:))` の固定サイズで、
  文字サイズ設定に追従しない作りのため、今回の変更に固有の問題は生じない（既存の設計事項）。
