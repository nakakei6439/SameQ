## 不合格の原因（これを直せば通る）

### [1]【最重要】実機でタイムラインが2〜3件目で固まり、二度と進まない

`SessionRequestQueue` が言語ペアごとに `TranslationSession` を**キャッシュして使い回す**設計そのものが、
Apple Translation Framework では成立しない。

- **再現手順（実機・端末言語 ja のまま）**:
  1. `-SameQFakeTranslate` を**付けずに** アプリを `-SameQResetState` で起動する
  2. 初回設定を終え、回答を投稿してタイムラインを開く
  3. 「次の人へ」を繰り返し押す
- **実際（実機3回とも同じ。乱数で順番が変わるので止まる位置は2〜4件目とばらつく）**:

  | 実行 | 端末言語 | 表示できた件数 | 止まった場所 |
  |---|---|---|---|
  | D01 | ja（端末そのまま） | 3件 | 4件目でスピナーのまま90秒 |
  | D02 (1回目) | en（`-AppleLanguages`） | 1件 | 2件目でスピナーのまま90秒 |
  | D02 (2回目) | en（`-AppleLanguages`） | 3件 | 4件目でスピナーのまま90秒 |

  90秒待っても次の回答は出ない。`Translator` の45秒タイムアウトは効かない（後述）。
  さらに、止まったあと**タイムライン画面そのものがアクセシビリティツリーから消える**
  （`timeline.close` も `timeline.loading` も存在しなくなる）。アプリのプロセスは生きたまま
  （pid は最後まで同一）なので、利用者からは「読んでいたら画面が勝手に閉じて、何が起きたか分からない」状態になる。
- **期待**: spec.md 194行「端末言語と異なる言語で書かれた回答が、タイムラインでは端末言語の文章として表示される」、
  196行「スワイプすると次の翻訳可能な回答が表示される」、199行「翻訳に失敗した回答は…スキップして次を表示する」
- **根拠（原因を切り分けた直接プローブ・実機 `EvalQueueProbeTests.testP6`）**:
  実装本体の `SessionRequestQueue` を本物の `.translationTask` に繋ぎ、
  「en のセッションを取る → 翻訳成功 → ko のセッションを取る → 翻訳成功 → **キャッシュ済みの en セッションで
  もう一度翻訳**」を実行したところ、3手目でフレームワークが致命的エラーを投げた:

  ```
  EVAL06P >>> P6 (1) en->ja = 私の猫がテーブルに飛び乗った。
  EVAL06P >>> P6 (2) ko->ja = 出勤の途中で靴を履いてきた。
  EVAL06P >>> P6 en セッションはキャッシュから同一インスタンス = true
  Translation/TranslationError+TranslationOnly.swift:64: Fatal error: Attempted to use
  TranslationSession after the view it was attached to has disappeared, which is not supported.
  Instead of storing a TranslationSession instance outside of the .translationTask closure,
  trigger a .translationTask to run again on a visible view and use that TranslationSession instance.
  ```

  `configuration` を別の言語ペアに差し替えた時点で前の `.translationTask` は畳まれ、
  そこで得たセッションは**無効になる**。`SessionRequestQueue.sessionsByKey` はその無効なセッションを
  持ち続け、同じ言語がもう一度来たときにそれを返す。
- **なぜアプリでは落ちずに固まるのか（症状の違い）**: プローブ（ユニットテスト内のウィンドウ）では
  致命的エラーになり、アプリでは `session.translate(_:)` が返ってこない形になった。どちらにせよ
  `AppSession.drawNextPost` の `await translator.translate(...)` が返らないので `timelineContent` は
  `.loading` のまま止まる。`SessionRequestQueue` の45秒タイムアウトは**セッションの取得**にしか
  掛かっておらず、`session.translate(_:)` の呼び出しには時間制限が無いため保険にならない。
- **起きる条件**: 「3つ目に**異なる**言語ペアを要求したあと、以前の言語ペアがもう一度来たとき」。
  同梱シードは1お題に15言語入っているので、実機ではほぼ必ず数件以内に成立する。
- **推測（症状とは分けて書く）**: 修正の方向は、セッションを保持せず
  **`.translationTask` のクロージャの中で翻訳まで済ませて結果だけ持ち帰る**形にすること。
  attempt 1 の eval で「優先度 高」として挙げた改善提案（`TranslationSession` をクロージャの外へ
  持ち出している）が、そのまま今回の不具合の原因になっている。
  併せて `session.translate(_:)` 側にも時間制限を掛けないと、返らない事態を検知できない。

### [2] 45秒タイムアウトで一度諦めた言語は、そのプロセスの間ずっと復帰できない（`invalidate()` が効いていない）

- **再現手順（`EvalQueueProbeTests.testP3`、シミュレータ・実機とも同じ結果）**:
  1. `.translationTask` を持つビューが載っていない状態で `SessionRequestQueue.request("en")` を呼ぶ → タイムアウトして `nil`
  2. ビューを載せる
  3. もう一度 `request("en")` を呼ぶ
- **期待**: `onNeedsSession` で `configuration?.invalidate()` を呼んでから同値の `Configuration` を入れ直しているので、
  `.translationTask` が再実行されてセッションが来ること（self-review が「保険」と書いている挙動）
- **実際**: `.translationTask` は再実行されない（`fireCount` は 1 のまま）。`request` は再びタイムアウトして `nil` を返す。
  ```
  EVAL06P >>> P3 request#1 (ビュー無し) got=false
  EVAL06P >>> P3 request#2 (ビュー有り・同じ en) got=false elapsed=3.05s fireCount=1 needs=["en", "en"]
  ```
- **推測（症状とは分けて書く）**: `self.configuration?.invalidate()` で現在の値を無効化した直後に、
  `self.configuration = TranslationSession.Configuration(...)`（invalidate 前と同値）で上書きしているため、
  SwiftUI が同一 run loop で見る最終値は変化していない。`invalidate()` は**差し替えずに現在の値へ対して**
  呼ぶ必要があるように見える。
- **影響**: 単体では致命ではない（[1] を直せばタイムアウト自体がほぼ起きない）が、
  「保険が実は効いていない」という点は self-review の記述と食い違う。

### 安定性

  **ちらつき（原文が一瞬見えてから翻訳に差し替わる）は 0 件**（切り替え直後のラベルと1秒後のラベルを毎回比較して確認）

  タイムラインが停止し、画面が消える。`~/Library/Logs/DiagnosticReports` に本評価中の新規クラッシュレポートは無い
  （既存の `SameQ-2026-08-18-070712.ips` は本評価開始より前のもの）
- **プローブ**: 実機で `TranslationSession` の使い回しがフレームワークの Fatal error を引き起こすことを確認（[1]）

### データ整合性（✓）
- `state.json` は `schemaVersion 4`。翻訳結果は**一切永続化されない**（`myPosts` に入るのは自分が書いた原文。
  実機・シミュレータとも確認）
- 既読の付き方は仕様どおり。シミュレータ疑似翻訳で通し読了後 `viewedPostIDs 31`（表示30件＋恒久的に非対応な `zxx` 1件）、
  再起動後も 31 のまま `timeline.exhausted` を維持
- 固着したときは既読が増えない（実機 D01/D02 とも `viewed 3` で止まり、読めていない回答が焼き付いていない）。
  attempt 1 の指摘4（一時的な失敗も既読になる）に対する修正は、永続層のレベルで動作を確認した
  （`EvalQueueProbeTests.testP5`、実ファイルの JSON を直接読んで検証）:
  - `nextTimelinePost(autoMarkViewed: false)` で引いただけでは `viewedPostIDs` は 0 のまま
  - 同じ巡回で引き直すと同じ回答が再び候補に出る（あとで再挑戦できる）
  - `excluding` を積むと `exhausted` に落ちて無限ループしない
  - `markPostViewed` を呼んだ時点で 1、既定の `nextTimelinePost(promptID:)` は従来どおり引いた時点で 2（回帰も維持）
- なお、シミュレータで疑似翻訳を**付けずに**通すと `viewed 31 / 表示 12`（ja端末）・`31 / 3`（en端末）・`31 / 2`（ko端末）に
  なる。これはこの環境の `LanguageAvailability` が全ペア `unsupported` を返し、実装がそれを「恒久的な非対応」と
  判定するため。判定自体は妥当（その端末では本当に永久に翻訳できない）なので不具合とは扱わない

## 改善提案（合否には影響しない）
- **[優先度 高]** 翻訳が1件も成立しない端末（モデル未取得・非対応言語）で回答が軒並みスキップされ、
  即「読み切り」になる。「いま読める回答がありません」に相当する状態を分けて出すと理由が伝わる（attempt 1 から継続）
- **[優先度 中]** `SessionRequestQueue.resolve` は `inFlightKey` が nil のとき到着したセッションを捨てている。
  遅れて届いたセッションをキャッシュに入れるだけでも、タイムアウト後の再挑戦が1回分速くなる（[1] を直したあとの話）
- **[優先度 中]** `Translator.textCache` に上限が無い（attempt 1 から継続・未対応）
- **[優先度 低]** `-SameQFakeTranslate` は `sessionQueue` の手前で分岐するため、**待ち行列と実セッションの
  協調部分をまったく通らない**。今回の [1] が疑似モードのUIテストを1本も落とさずに通ったのはこのため。
  疑似モードでも「セッションの取得と失効」を模擬できるようにしておくと、同種の不具合を実機前に捕まえられる

  `-AppleLanguages` によるプロセス単位の上書きで代用した
