## 不合格の原因（これを直せば通る）

### [1] 同じ言語ペアの翻訳要求が2回目で永久に止まる（`Translator` の待ち行列が復帰不能に詰まる）

- **症状（実測）**: `Translator` の待ち行列の実装（`requestSession` / `startNextIfNeeded` / `resolve`）をそのまま写したものを `.translationTask` 付きのホストビューに繋いで動かすと、
  - 1件目の要求（en → 端末言語）: セッションを受け取れる
  - 2件目の要求（**同じ en → 端末言語**）: 20秒待っても**セッションが来ない**
  - 3件目の要求（別ペア ko → 端末言語）: これも来ない（2件目が `pending` の先頭に残り `isSessionInFlight == true` のままなので、以後どの言語ペアも要求が出せない）
- **直接の原因（実測）**: `.translationTask(configuration)` は、**値の等しい `TranslationSession.Configuration` を代入し直しても再実行されない**。別プローブで確認した発火回数:
  - 1回目 `Configuration(en, ja)` を代入 → 発火 1
  - 2回目 **値が同じ別インスタンス**を代入 → 10秒待っても発火 **1 のまま**
  - 3回目 `Configuration(ko, ja)` を代入 → 発火 2
  - 4回目 `Configuration(en, ja)` を代入 → 発火 3
  `Translator.startNextIfNeeded()` は毎回 `TranslationSession.Configuration(source:target:)` を作って `configuration` に代入するだけなので、**直前と同じ言語ペアだと `.translationTask` が動かず、`withCheckedContinuation` が永久に再開されない**。
- **期待**: spec.md 194行「端末言語と異なる言語で書かれた回答が、タイムラインでは端末言語の文章として表示される」、198行「今日のお題も端末言語で表示され」。2件目以降の回答も同じように翻訳されて表示されること。
- **この状態でユーザーに見えるもの（コード経路からの推測。画面上での再現は環境上できていない → [2]）**:
  - `AppSession.drawNextPost` の `await translator.translate(...)` が返らない → `timelineContent` が `.loading` のまま → タイムラインがスピナーのまま固まり、以後どのボタンでも進まない（`advanceTimeline` は `drawNextPost` を呼ぶだけで、前の呼び出しが返っていない）
  - `AppSession.syncPromptTranslation` の場合は `promptDisplayText` が nil のまま → お題が「準備中…」から戻らない
- **起きる条件**: 翻訳要求が**連続して同じ原文言語**になったとき。
  - 端末言語が日本語以外（英語・韓国語など）: お題（ja → 端末言語）を翻訳した直後に、ja の回答（prompt_001 では31件中13件）を引いた時点で成立。ほぼ即座に詰まる。
  - 端末言語が日本語: 外国語の回答を続けて2件引き、その2件の言語が同じとき（en3件 / es2件 / ko2件があるので通しで読むと十分起こりうる）。
- **根拠**: 本評価で実行したプローブのログ
  ```
  EVAL06 >>> PROBE request#1 (en) got session = true
  EVAL06 >>> PROBE request#2 (en, 同じ言語ペア) got session = false ← 20秒待っても返ってこない
  EVAL06 >>> PROBE request#3 (ko, 別の言語ペア) got session = false
  EVAL06 >>> PROBE fireCount after 1st assign = 1
  EVAL06 >>> PROBE fireCount after 2nd assign (same pair) = 1
  EVAL06 >>> PROBE fireCount after 3rd assign (different pair) = 2
  ```
- **推測（症状とは分けて書く）**: `TranslationSession.Configuration` に `invalidate()` が用意されているのは、まさに「同じ設定でもう一度セッションを作り直す」ためだと思われる。修正の方向としては (a) 代入前に既存 `configuration` を `invalidate()` する、(b) 受け取ったセッションを言語ペアごとに保持して使い回す、(c) 万一セッションが来なかったときのタイムアウトを入れて `nil` を返しスキップに落とす、のいずれか。**(c) は単独では不十分**（毎回タイムアウト待ちになる）が、固まらないための保険としては要る。

## 改善提案（合否には影響しない）
- **[優先度 高]** 翻訳が1件も成立しない端末（モデル未取得・非対応言語）で、回答が軒並みスキップされて即「読み切り」になる。**そのとき既読にしない**（[4]）だけでなく、「いま読める回答がありません」に相当する状態を分けて出すと、ユーザーが理由を推測できる
- **[優先度 高]** `TranslationSession` を `.translationTask` のクロージャの外へ持ち出して `translate` を呼んでいる（`Translator.resolve` は continuation を再開して即座にクロージャを抜ける）。Apple のドキュメントはセッションをタスクのスコープ外で使わないよう書いている。このシミュレータでは in-scope / out-of-scope とも同じ `unsupportedLanguagePairing` が返るため**判別できなかった**が、実機で確認する価値がある
- **[優先度 中]** `Translator` の `textCache` に上限が無い。1お題あたりの件数なら問題ないが、上限か有効期限を付けておきたい
- **[優先度 中]** 検証しやすさ: `Translator` は `init(availability:)` で差し替えられるのに `AppSession` の既定値が `Translator()` 固定で、起動引数から差し替えられない。`-SameQFakeTranslate` のような Debug 限定の疑似翻訳（例: 本文の頭に言語コードを付けて返す）があれば、シミュレータでも [1] のような詰まりが UI テストで検出できる
